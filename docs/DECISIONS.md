# OneServer 长期决策与踩坑

本文件记录仍约束当前实现、或很容易被误判为 bug 的设计。编号保持与源代码注释兼容，可稀疏；已不再有影响力的阶段记录、会话日志和完成清单不保留。需要变更某项结论时，同时更新实现、测试和本文件。

## 架构、执行与安全

| 编号 | 结论 | 原因与后续约束 |
|---|---|---|
| D2 | 先建立框架和可验证规范，再迁移功能。 | 不以 lint 豁免或旧实现替代工程约束；新代码不得加入豁免表。 |
| D5 | 运行时零额外依赖。 | 最小系统未必有 `jq` 等工具；库与脚本以 Bash/coreutils 和已声明的系统工具实现。 |
| D8 | 注册表是命令发现的单一事实源。 | CLI、菜单与补全均由元数据派生；新增命令不应修改前端。 |
| D9 | “有副作用且需读取输出”是独立执行类别。 | 必须用 `os::run_out`，不能以只读 query 绕过 dry-run。 |
| D10 | 同一系统事实只能有一个 probe 实现。 | 多消费者需求进入 `probe.sh`，避免不同界面给出矛盾结论。 |
| D14 | 命令派发和更新切换必须 `exec`。 | 避免父进程继续从被替换的脚本读取字节。 |
| D15 | 会谎报成功的 dry-run 比没有更危险。 | 通过 `OS_RUN_SKIPPED` 区分跳过与无输出；预演不产生变更。 |
| D18 | probe/query 必须有超时。 | 菜单和诊断不能因挂起的服务、挂载或 Podman 永久阻塞。 |
| D23 | 锁放 `/run/oneserver`，不放 `/tmp`。 | 防止 root 跟随攻击者预置的符号链接。 |
| D25 | 不提供可覆盖的路径配置。 | root 进程路径不能被外部环境或配置改变。 |
| D26 | 不缓存注册表。 | 少量脚本扫描成本低，缓存会静默过期。 |
| D27 | 使用单一全局锁。 | apt、Podman 已有自身串行机制；分域锁只引入顺序和死锁风险。 |
| D28 | 不为尚无稳定产品边界的容器能力设计接口。 | 不把薄封装或未验证接口写入支持面。 |
| D32 | 菜单编号按屏重排 1..N；`@order` 只决定排序，不上屏。 | 一个字段兼任「排序权重」与「屏幕上的选择键」的代价是：二级菜单打的是 51..55，虚拟项「备份与恢复」编号 38 而它的成员是 33/34，同一次操作连按三层看到 25 → 51 → 1。编号改为每屏从 1 数起后，`@order` 收窄成**组内**唯一（见 D221），只服务于排序；顶层直接敲子条目编号的旧路径随之删除，改由输入命令名直达（`registry::resolve` 最长前缀）。 |
| D33 | 脱敏按值而非参数位置。 | 位置变动会静默泄密；短凭据值拒绝作为脱敏值。 |
| D35 | 组件标识为 `<type>[:<instance>]`。 | state、依赖、unit 和卸载都使用完整标识，支持多实例。 |
| D36 | unit 必须标记 `own:` 或 `ext:`。 | 外部软件包的 unit 只能停止/禁用，绝不删除其文件。 |
| D39 | state 使用行式格式，JSON 仅用于输出。 | 不依赖 jq，局部损坏不应让全部 state 无法恢复。 |
| D40 | 信号中断不执行回滚栈，退出 131。 | 中断时系统状态未知；临界区保护无法安全中断的序列。 |
| D44 | probe 的实时/缓存来源和时间必须可见。 | 非 root 不能把旧快照伪装为实时事实。 |
| D47 | CI 规则须区分完备检查与启发式检查。 | 不能把无法静态判定的规则伪装成完整保证。 |
| D46 | 菜单分组是 `groups.conf` 中的产品数据。 | 添加或改名分组不应改变框架规范；注册表校验脚本引用。 |
| D51 | 配置 key 与 L0 变量同名。 | 白名单由现有变量自然形成，避免维护第二张映射表。 |
| D53 | 配置加载和校验属于 bootstrap。 | L0 只能含常量；校验需在 L1 初始化之前完成。 |
| D56 | lib 模块不互相 source。 | bootstrap 和测试辅助是唯一明确装配路径。 |
| D57 | warn/error 默认走 stderr。 | 使正确输出流成为默认，避免失败信息被日志重定向吞掉。 |
| D59 | `log.sh` 属于 L1。 | `errors.sh` 需要单向依赖日志，不能用同层依赖破例。 |
| D62 | `exec.sh` 属于 L2。 | probe、systemd 与模板能力都需要它；下沉可避免 L3 同层依赖。 |
| D63 | `--env` 通过子 shell export 后 exec。 | `env K=V command` 会把秘密暴露在 argv。 |
| D64 | 命令自身输出也必须先脱敏再写日志。 | token、连接串可能由命令回显，不只来自框架命令行。 |
| D65 | SQL 客户端显式设置字符集。 | Ubuntu/MariaDB 组合可能静默损坏四字节字符。 |
| D68 | probe 不打印返回值。 | 通过变量返回以保留来源、年龄和状态，避免命令替换子 shell。 |
| D69 | `systemd.sh` 收集 touched unit，由 L4 落 state。 | 保持 L3 模块无同层依赖。 |
| D70 | 呈现语义、受控配置、交互和 JSON 信封在 bootstrap。 | 它们组合多层能力，不应制造反向依赖。 |
| D73 | manager 命令按一个脚本加动作参数实现。 | 既保留非交互 CLI，又避免一个动作一个脚本的膨胀。 |
| D72 | 测试不能要求产品路径可由环境覆盖。 | 以一次性容器测试真实路径，不能为方便测试扩大 root 配置攻击面。 |
| D74 | `run_out`、`query`、SQL 查询都通过变量返回输出。 | stdout 会污染调用者或丢失运行状态。 |
| D79 | 菜单常驻，但每轮结束 `exec` 自己重载。 | 命令跑在独立子进程；菜单靠 exec 自身取得新 lib 与新注册表。文件替换一律换 inode，常驻进程读不到变化的字节，K13 因此不适用于菜单。 |
| D86 | 补全动态查询注册表。 | 静态候选表会落后于已安装脚本。 |
| D91 | 组合数组或参数前显式设定空格 IFS。 | 全局换行 IFS 会把审计和错误报告拆成误导性多行。 |
| D92 | bootstrap 最早安装信号兜底 trap。 | 装配窗口收到信号也必须一致返回 131。 |
| D93 | 管理 PHP 配置依据真实 probe，不依据 state 依赖。 | 手工安装的 PHP 不在本工具 state 中，但仍可安全管理。 |
| D94 | 模板渲染后残留占位符即拒绝写入。 | 半渲染配置会以难以定位的方式导致服务失败。 |
| D138 | 不带实例的 `@requires` 在 state 缺失时可回退到 probe。 | state 只表示本工具安装过的内容；带实例约束不得回退为不精确探测。 |
| D205 | 「默认清单 + 用户增删」统一走 `os::multiselect`。 | 裸名字与 `+/-` 混用、命令行里出现序号、序号既挑又排一律以退出码 2 拒绝；减不掉的项告警而非静默忽略。序号只在交互内有效，清单可被 conf 覆盖后序号会漂。 |

## 分发、安装与系统资源

| 编号 | 结论 | 原因与后续约束 |
|---|---|---|
| D97 | 校验失败不能降级到未校验来源。 | 区分不可达与校验失败；后者必须硬失败。 |
| D98 | 校验文件同时兼容裸哈希与带文件名格式。 | 不依赖 `sha256sum -c` 的单一格式。 |
| D99 | 包管理接口放在 bootstrap。 | 它同时依赖 probe、执行、临界区和变更记录；不新建违规层。 |
| D101 | 旧脚本不构成新代码规格。 | 先回答装、配、查、升、卸；个人偏好可覆盖，机器事实先 probe。 |
| D103 | 资源清单只登记组件私有包。 | 通用依赖不能因卸载一个组件被 purge。 |
| D106 | Caddy 插件清单可由受控默认配置覆盖。 | 保证用户可组合插件，同时保持来源和校验边界明确。 |
| D107 | 插件参数支持保留、增、减、替换和 `none`。 | 零输入应可采用默认清单；比较前按确定顺序处理。 |
| D108 | 插件组合排序去重后比较。 | 同集合的不同输入顺序不得破坏幂等。 |
| D110 | Redis 使用发行版源，版本升级交给 apt。 | 不引入未经评估的第三方源和额外生命周期。 |
| D118 | state 与 secure 在 dry-run 下不得写入。 | 预演写入会破坏随后幂等与凭据一致性。 |
| D121 | OneServer 自身以 root 的 unix socket 连接 MariaDB。 | 不把用户 root 密码当作内部依赖。 |
| D125 | state 记录系统事实，而非本次意图。 | 诊断和卸载必须基于当前真实状态。 |
| D126 | 实际安装包本身就是一次变更。 | 用户可见结果不能只统计配置文件变化。 |
| D135 | 脚本辅助函数也以变量返回值。 | `printf` 加命令替换会把提示文字混入数据。 |
| D140 | 删库和恢复前先备份，备份失败即停止。 | 不可逆操作需要可用副本，而非仅一次确认。 |
| D149 | Caddy 管理使用动作式 CLI，不保留常驻二级菜单。 | 与一次性菜单、可脚本化命令和安全 trap 模型一致。 |
| D179 | manifest 从仓库内容生成且不入库。 | 手写清单是第二事实源；含 commit 的发布清单应作为产物。 |
| D184 | 卸载只按资源清单逆序执行。 | 禁止按组件名分支、猜测或自动删除用户数据。 |

## 容器引擎：Podman 与 Docker

| 编号 | 结论 | 原因与后续约束 |
|---|---|---|
| D191 | 不安装 podlet 或 jq。 | 本工具直接生成所需 Quadlet，避免可选转换器和额外依赖。 |
| D194 | 不存在的宿主绑定路径直接拒绝。 | 自动创建空 root 目录会把拼写错误伪装成成功。 |
| D196 | Compose 项目用自有 systemd wrapper 托管。 | 重启后可恢复，并可作为受控 `own:` 资源登记。 |
| D197 | wrapper 的 `ExecStop` 使用 `stop`，不用 `down`。 | systemd restart 不得删除容器、网络或匿名卷；显式 down 才可删除。 |
| D198 | Compose 项目目录原地使用，不复制。 | `.env`、引用文件、相对挂载和 build 上下文必须保留原语义。 |
| D199 | Compose 项目名禁止 `.`。 | 防止 unit 名规范化后与下划线名称冲突。 |
| D201 | Compose 幂等比较渲染后的 `compose config`。 | 仅比较 compose 文件会漏 `.env` 等依赖，哈希全目录又会包含运行数据。 |
| D202 | 卸载 compose 只停止；删除容器/网络须显式 `compose rm`。 | 通用卸载器不能为组件添加分支或隐式执行 down。 |
| D203 | 添加时选择并固定 Compose provider。 | provider 的兼容性不同，unit 必须复用已验证 provider。 |
| D204 | 已托管项目不自动切换 provider。 | 不同 provider 的标签与网络语义不兼容；只有无容器时可重新选择。 |
| D205 | Docker 走官方源 docker-ce，与 podman 的发行版源（D110）相反。 | 发行版的 `docker.io` 落后一到两个大版本，而 `docker compose` 与 buildx 由 Docker 以插件形式发布，跟官方源才配套。代价是一条第三方源与一份密钥，两者都登记进资源清单。 |
| D206 | 公网定位对 Docker 落在 `daemon.json` 的 `"ip"`，不落在防火墙。 | dockerd 把自己的跳转插在 FORWARD 链最前面，ufw 的 `DEFAULT_FORWARD_POLICY` 与放行规则对已发布端口一律不生效；靠防火墙保护 Docker 得到的是「看起来两边都对、实际毫无防护」。绑定地址只对新建容器生效，已有容器只能列出由人重建。 |
| D207 | 用户自己的 `daemon.json` 不覆盖；公网定位下无法确认绑定地址即拒绝安装。 | 覆盖它等于删用户配置（§12），装完不管则公网定位的承诺是假的。§15：补偿控制落实不了就拒绝执行。 |
| D208 | 装 Docker 撞上 podman-docker 时确认后代为 purge，并从 state 摘掉那条 pkg。 | 两者提供同一个 `/usr/bin/docker`，dpkg 装不到一起。podman-docker 是本工具装的、撤销可控，与 install_podman 撞上真 Docker 时直接拒绝不对称是有意的。留着那条 pkg 记录就是假事实，而 state 是卸载的唯一依据。 |
| D209 | Docker 容器不进 state，dockerd 自己就是账本。 | 容器不是 pkg/file/divert/alt 中的任何一类，登记进去卸载器也做不了什么；而 podman 容器要登记是因为它对应一个 Quadlet 文件与一个 unit。因此 `oneserver docker` 对全部 Docker 容器一视同仁，不分「本工具托管」。 |
| D210 | `docker run` 只补 `-d`、`--name`、`--restart`，其余 flag 原样透传。 | 与 podman 侧必须逐个翻译成 Quadlet 相反：这里不改写语义，认不出的 flag 最坏也只是 docker 自己报参数错误，所以不需要 flag 表。|
| D211 | 建容器（`podman run` / `docker run`）拆成独立脚本，与容器管理（`podman` / `docker`）分开。 | 翻译一条 run 命令的代码量（切词、flag 表、Quadlet 生成）跟「看/启停/删已有容器」不是一类事。`@command` 沿用 `podman run`/`docker run` 而不是改成 `create`：靠 registry 两词最长前缀匹配直接命中新脚本，用户已有的命令行一个字不用改。 |
| D212 | `groups.conf` 的 `order` 是**一条全局数轴**，顶层分组与收纳分组共用；挂哪个父级只决定折叠层级，不决定排序位置，两者必须手动对齐。 | 收纳分组在菜单里的位置由它自己的 `order` 决定，而不是由父分组的。两者不对齐时 `registry::sort` 会把它排到后续分组之后，父分组的标题于是断开、重复出现一次。因此 `templates/groups.conf` 按最终要显示的顺序从 10 起每档 10 写，间隔正是留给以后往中间插分组用的。子脚本的 `@order` 不受此约束，它只在自己组内比较（D221）。 |
| D213 | 容器自动更新两侧都随时可切，但机制不同：Podman 改 Quadlet 文件里的标签，Docker 改本工具自己维护的名单。 | Podman 有 `.container` 文件可编辑，改完 `daemon-reload` + 重启服务即可让新标签生效。Docker 不支持给已有容器改标签（`docker update` 只管资源限制与重启策略），所以标签模式下想给一个跑着的容器开自动更新只能删了重建 —— 于是改用名单（D224）：谁要更新记在本工具这边，切换只重建更新器自己那个容器，用户的业务容器一动不动。**两侧都是「标签/名单 + 执行者」两件事，缺一不成**：只登记不开执行者，表现是「切了自动更新却什么都没发生」，所以两侧的列表页都要同时显示这两件事的状态，两屏都要有开启/关闭执行者与手动跑一轮的动作。 |
| D214 | Docker 自动更新走 Watchtower，**按容器名单筛而不是按标签筛**，镜像用 `nickfedor/watchtower`，且视作普通容器不进资源清单。 | Docker 没有 podman 的 Quadlet + `podman-auto-update.timer` 原生机制，业界通行做法是部署 Watchtower 盯 `docker.sock`。**筛选方式从 `--label-enable` 改成传容器名单**，理由见 D224。**名单空时绝不能起它** —— 不带名单等于扫全机，正是「不在名单里的一概不动」的反面。**原始的 `containrrr/watchtower` 已停止维护**（`latest` 停在 2023-11），内嵌 Docker 客户端只认到 API 1.25，在较新的 Docker Engine（验证环境 29.x，要求 API ≥ 1.40）上直接进重启循环——`nickfedor/watchtower` 是社区接手维护的延续，构建是新的，本地验证过能正常拉起。Watchtower 本身就是个 docker 容器，跟 D209 一样不登记进资源清单，卸载 docker 不特殊清理它。 |
| D215 | 引擎名写进 `@name`（`Podman 容器` / `Docker 容器`），**不为区分引擎新增分组**；`@self_name` 仍是不带引擎名的「容器列表与操作」。 | 两个引擎的容器管理脚本 `@name` 都叫「容器管理」时，两个引擎都装的机器上「容器」那一屏就是两条看不出区别的条目（只装一个时该组只剩一个成员、被 D216 跳过，所以长期没暴露）。加两个分组也能区分，但那是在 `@command` 已经写明引擎之后再立一份声明，还多一层导航；`@name` 一行就够。进去之后标题栏已是 `容器 › Podman 容器`，第一项由 `@self_name` 承担，不必重复引擎名。折叠在下面的 `podman image`/`volume`/`compose`/`run` 两边同名，但永远不同屏。 |
| D216 | 分组虚拟项展开后只剩一个成员时自动跳过，直接进那个成员。 | 「分组下只有一个成员」的结构（如 `db` 组只有 `db_manager.sh`）会产生只有一项的展开列表，逼用户多确认一次没有意义；落在 `bin/oneserver-menu` 的 `menu_loop`（导航路径栈那一圈），不影响本来就有多个成员的分组。 |
| D217 | 不做「读 `docker inspect` → 删 → 按反推的配置重建」的自动化。 | 这条最初是用来解释「docker 侧只能只读查看」的，名单模式（D224）之后前半截不再成立 —— 切换自动更新已经不需要碰用户的容器。但结论本身保留且更普遍：`docker inspect` 反推的参数覆盖不了所有场景（自定义网络、复杂 mount 等），任何「替用户重建容器」的自动化都有把配置重建走样的风险，而走样不报错。用户确实要改容器参数时，本工具给的是当初那条 run 命令的存档（D226），由人改完重新粘，不替他猜。 |
| D218 | `docker compose` 复用 `podman_compose.sh` 的 systemd wrapper 模型（own: unit + state 命名空间 `docker-compose:`），但去掉 provider 挑选。 | Docker 上 `docker compose` 就是官方 Compose v2 插件，没有 podman 那边「podman-compose / v1 / v2 混杂，要挑并钉住」的问题（D203/D204），provider 检测整段不需要。**state id 用 `docker-compose:` 不是 `compose:`**：两个引擎各自独立注册，同一个项目名在两边分别托管不会在 state 里撞车；unit 前缀同理用 `oneserver-docker-compose-`，避免与 podman 那边的 `oneserver-compose-` 撞同一个 systemd unit 名。包一层 systemd 的理由（D196）在 docker 上同样成立：`docker compose up -d` 起的容器开机自不自动回来，取决于用户 compose 文件里写没写 `restart:`，而本工具不改用户的 compose 文件（D198），wrapper unit 让这件事不依赖 compose 文件本身怎么写。 |
| D222 | `lib/theme.sh` 只保留有原语真在消费的 key；`OS_THEME_SYM_ARROW` / `_BULLET` 及其 `_ASCII`（4 个）随本次一并删除。 | theme.conf 的 key 就是 theme.sh 的变量名，而 §14 把 `/etc/oneserver/*.conf`的 key 列为「只增不删」。这 4 个是例外：`ui::_load_symbols` 从来只解析用得上的那几个符号，它们**从未被任何原语读取过** —— 用户即使在 theme.conf 里设过，也从来没产生过任何效果。「只增不删」保护的是曾经生效的配置，而不是一个设了也没用的开关；留着它才是把死配置伪装成能用的。全仓已确认零引用，故按次版本发布而不是主版本 +1。 |
| D220 | 一个管理屏由 `ui::frame_begin` / `ui::menu --keep-screen` 组成同一布局上下文；仅画左侧树状引导（`╭`、`├`、`│`）；标题下保留一行延续线，导航前以 `╰────` 收住，不画右边框。 | 窄终端中外框与整行横线会比正文先折行，且让宽度计算误差格外显眼；左侧引导只占一格，标题下的延续线维持紧凑留白；导航前的横线仅随菜单宽度延展，仍可直观表示层级。组合状态仍在渲染层，脚本无需拼接样式；`ui::menu` 完成后结束该状态，避免后续输出继承布局。表格仅以列间留白分隔，所有文本按显示宽度截断。 |
| D221 | `@order` 组内唯一、步长 10；菜单编号按屏重排 1..N。 | 见 D32。全局唯一的代价是加一个脚本得先全仓找一个没被占的号、还得落在正确的号段里 —— 那是把「排序」和「屏幕上的选择键」两件事塞进同一个整数造成的。拆开之后，换位置改 `@order`、换归属改 `@group`、收进子菜单加 `parent`，全在数据里，框架文件与规范文件一行不动。步长 10 是为了往中间插入时取中间值，不必推动其余各条。 |
| D219 | `templates/groups.conf` 按 `|` 切字段，显示名可含 ASCII 空格。 | 原先按空白切字段，于是显示名里不能有空格，「Podman 容器」只好写成夹一个全角空格（U+3000）的「Podman　容器」——屏幕上那是个两格宽的洞，而根源只是分隔符选错了。换成 `|` 之后各字段两端的空白一律去掉，显示名恢复自由，全角空格这个绕行方案随之作废。 |
| D223 | 建容器时**首词指名的引擎必须与入口一致**，不一致即以退出码 2 拒绝，两侧对称。 | 从前 podman 侧不看首词（它只把命令当文本翻译成 Quadlet），docker 侧把首词当噪音吃掉（剩下的按 D210 原样透传）。于是两个引擎都装的机器上，同一条 run 命令在哪个入口粘都成功 —— 实测把同一个应用在两边各建了一份、各占一个宿主端口，而 `podman ps` 与 `docker ps` 互相看不见，任何一边都看不出另一边还有一个。首词是用户唯一表达过的「这条命令给谁」，读得到就不该丢。podman 侧因此不再接受 `docker run` 写法：它只读文本、技术上翻译得了，但代价是意图被无声改写。docker 侧另有硬理由 —— podman 独有的 `--userns=keep-id`、`--pod`、挂载的 `:Z`/`:z` docker 不认。**拒绝必须给出下一步**（另一个引擎装着就指路过去，没装就明说改哪个词），否则用户删掉首词再粘就绕过了这道拦截，而且什么提示都没有。 |
| D224 | Docker 侧的自动更新改为**名单驱动**：要更新哪些容器记在 state 的 `docker` 组件下（`autoupdate` 键，空格分隔的容器名），更新器启动时把名单作为参数传给它。 | 标签模式的死结是 docker 不能给已有容器改标签，用户想事后调整只能删了重建，而重建有走样风险（D217）。把「谁要更新」从容器身上挪到更新器身上就解开了：改名单只需重建更新器自己那个容器，它无状态、重建零风险。实测确认（Docker 29.7.2 + watchtower 1.20.3）：不给名单扫全机 5 个容器，给一个名字扫 1 个，给两个扫 2 个，常驻模式同样认名单；**名单里有不存在的容器名不报错，安静跳过**，所以用户绕过本工具删容器只会留个无害的孤儿名，列表页提示、不自动清（自动清会在容器临时删掉重建的窗口里把用户的设置一起抹掉）。名单不是 pkg/file/divert/alt 中的任何一类，故用普通单值键而不是资源清单的多值键。 |
| D225 | 开关 Docker 的自动更新服务用**建/删更新器容器**，不用起/停；且这是全项目唯一创建更新器的地方（`install docker` 不再部署它）。 | 名单是更新器的**启动参数**，停了再起用的还是老名单 —— 删了重建才能保证跑着的那个与名单永远一致。停而不删还有第二个坑：它是 `--restart always` 建的，重启机器自己就回来了，用户以为关掉了其实没有。**装 Docker 的那一刻名单必然是空的**（机器上一个容器都没有），部署它要么无事可做、要么只能不带名单起，所以 `install docker` 整段删掉、`--watchtower` 参数一并删除，只留一句指路。实测还发现：**新起的常驻 watchtower 会删掉机器上其它 watchtower 容器**（它自带的单实例保护，日志写 `removed_instances`），对重建是好事，但用户自己另装的更新器会被干掉，所以开启时必须说这句；**一次性的 `--run-once` 实例不触发这个清理**，所以「立即检查更新」用它，常驻的跑着也不受影响。 |
| D226 | 建容器时把用户粘的那条 run 命令**掩码后**存档：podman 写进 Quadlet 文件的注释，docker 打成容器自己的一个标签（`io.oneserver.run-cmd`）。 | 事后要改容器参数，手上有当初那条命令比读 Quadlet 的 key 名或反推 `docker inspect` 方便得多，而 docker 侧本来就没有第二份配置。跟着容器走（标签随容器删除而消失、Quadlet 注释随文件走）而不是另立一份账，生命周期才对。**掩码的理由不是文件本身的保密**——同一份文件里 `Environment=` 那几行、`docker inspect` 的 `.Config.Env` 都已经是明文了；它挡的是「这一行最可能被整条复制出去」（贴进工单、聊天、笔记）。代价是存档不能原样重跑，所以那一行里把「凭据值已掩码，重跑前补回」写明。 |
| D227 | `docker run` 执行时把识别出的凭据值经 `--secret-val` 交给执行封装登记脱敏。 | 在此之前 docker 侧是把用户整条命令原样交给执行封装的，而日志记的就是那条命令 —— 一条带 `-e MYSQL_ROOT_PASSWORD=…` 的命令，密码直接明文进日志，违反不变量第 4 条。podman 侧不中招是因为它翻译成 Quadlet 文件、不把命令交给引擎。识别判据是环境变量名转小写后含 `pass`/`token`/`secret`/`key`（转小写是必须的，`Password`、`apiKey` 这类混写最常见）。执行封装拒绝登记短于 6 个字符的值（短值全局替换会把整行打成马赛克，毁掉排查证据），碰到这种如实警告它会明文进日志，不假装已脱敏。 |

## 已核销问题留下的规则

这些 `K` 编号不再是待办，而是仍会造成安全、数据或可用性事故的反例。

| 编号 | 失败模式 | 后续约束 |
|---|---|---|
| K1 | 凭据文件写入或删除破坏了无关条目。 | secure 只经专用原子接口修改，按命名空间清理。 |
| K2 | 不安全的网络监听默认开启。 | 降低安全性默认 `n`，同步实施补偿控制。 |
| K3 | 数据库账号默认通配来源和过宽授权。 | 默认最小权限与本地来源；扩大范围需显式选择。 |
| K4 | `eval` 与拼接命令导致凭据泄露或 root RCE。 | 禁止 eval，命令以数组和受控接口执行。 |
| K5 | `/tmp` 锁可被符号链接攻击。 | 锁和敏感临时文件仅位于受控 `/run` 目录。 |
| K6 | 管理定时任务误清空用户既有任务。 | 只管理自己登记的资源，不能覆盖未知用户资产。 |
| K7 | 多实例覆盖另一实例的凭据或 state。 | 使用完整实例标识和命名空间。 |
| K8 | 失败信息被重定向，终端静默。 | warn/error/失败报告走 stderr，日志不替代用户可见错误。 |
| K9 | SQL 字符串拼接。 | 只使用 SQL 转义接口和安全默认连接方式。 |
| K10 | root 管道执行第三方远程脚本。 | 下载先校验，再处理；不执行未经验证远程内容。 |
| K11 | 安装器以旧标记短路，不能修复重装。 | 安装器以 manifest 与目标状态校正，不以历史标记跳过。 |
| K12 | source 配置或凭据文件。 | 严格解析允许的键值，不把数据当代码执行。 |
| K13 | 覆盖正在执行的脚本。 | 派发和更新用 exec，切换器原子替换并支持回滚。 |
| K14 | 探测无超时导致界面卡死。 | 所有 probe/query 有超时和显式降级状态。 |
| K15 | 运行时从网络取模板。 | 模板随分发落地，只读取本地受控目录。 |
| K16 | 前置权限检查发生得太晚或信息不清。 | bootstrap 在副作用前统一校验权限并用专属退出码。 |
| K17 | 模板指向不存在的日志路径。 | 写入模板前验证相关目录/服务语义，测试覆盖实际落地。 |
